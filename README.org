#+TITLE: Sovereign Computing Environment & Node Specification
#+AUTHOR: Esperoj
#+STARTUP: overview
#+FILETAGS: :system:

· Goal

One plain-text repository that commissions and maintains the same personal computing environment on every node — for decades, without platform lock-in, vendor fatigue, or maintenance burden. Pragmatic, not ideological.

| Node      | Host                 | Profile       | Privilege                |

|-----------+----------------------+---------------+--------------------------|

| PC        | Debian 13+           | ~desktop~     | user + sudo              |

| Phone     | Android / Termux     | ~phone~       | user, no root            |

| Pubnix    | shared rootless UNIX | ~pubnix~      | user only                |

| Container | Debian 13-slim image | ~docker-base~ | user + passwordless sudo |

A fresh node must be commissionable from nothing but a login: either an SSH agent forwarded from a trusted machine, or one encrypted seed file carried over by hand.

Non-goals: multi-user hardening, offline-first installs, configuration frameworks, checksum verification of fetched binaries.

This document describes the system as it actually behaves — including where it deliberately bends its own rules. Where code and this file disagree, one of them is wrong; fix it.

· Axioms, with their honest boundaries

| Axiom                  | Working rule                              | Where it bends                                                          |

|------------------------+-------------------------------------------+-------------------------------------------------------------------------|

| 1. Pragmatic Longevity | POSIX sh, GNU Make, Git, Stow, plain text | bash where pipefail/arrays earn it; the shebang is the source of truth    |

| 2. Anti-Complexity     | the build model fits in your head         | one deliberate make idiom (foreach + include), used uniformly             |

| 3. Structural Safety   | loud failures, strict perms, backup first | installs need network; rootless hosts get a loud skip, not a fake install |

| 4. Pragmatic Flow      | millisecond no-ops, standalone CLIs       | a profile switch re-runs the installer once for the new package set       |

** Axiom 1 — Pragmatic Longevity

Foundations: POSIX sh, GNU Make, Git, plain text, GNU Stow (~--no-folding~), standard UNIX utilities. Everything inspectable with ~cat~, ~find~, ~grep~. bash allowed where it earns its keep (~pipefail~, arrays) — visible in the shebang. On FreeBSD ~make~ is ~gmake~.

Avoided: configuration frameworks, dotfile DSLs, state daemons, formats needing special tooling.

** Axiom 2 — Anti-Complexity

· No external state database. State is the filesystem plus make's in-memory DAG.
· Single-phase evaluation. Nothing persists except ~.state/~, disposable at any moment (~make clean-state~).
· Each dependency declared exactly once. A profile's module list drives loading and build order.

** Axiom 3 — Structural Safety

· Loud failures. Package installs, binary fetches, and ~vault sync~ abort with visible errors and nonzero exits.
· Strict vault permissions. =~/.vault= clamped to 0700 dirs and 0600/0700 files on every apply/sync, on demand via ~vault chmod~.
· Backup before overwrite. ~dot~ keeps an unmanaged host file blocking a link beside itself as ~.a.bak~ (latest wins) — never destroys it.
· Network honesty. Applying config is offline (stow, vault apply, prune, lint, fmt). Installing is online and fails loudly without network. Offline-safe for everything that does not fetch, not offline-first.
· Rootless honesty. Without provably usable privilege, ~install-sys-pkg~ prints a loud skip listing what the host must provide, exits 0 so fetch fallbacks run. Never pretends to install, never asks for a password it could not use; a ~sudo~ binary on PATH or a seat in an admin group is never read as privilege — sudo answers for itself, non-interactively, or not at all.

** Axiom 4 — Pragmatic Flow

· Shell startup performs zero work: no compilation, no network, no linking.
· An unchanged package set re-runs in milliseconds (~0.2s measured for a full ~make base~).
· Core CLIs (~dot~, ~vault~, ~install-sys-pkg~, ~install-tool~, ~fetch-bin~) run standalone once ~make base~ installed them; Make is orchestration, not a runtime dependency.

** Goal-driven includes, single-list profiles

~make <target>~ includes ~modules/<target>/<target>.mk~ (root Makefile, ~foreach~ over ~$(MAKECMDGOALS)~). Leaf modules pull deps via ~include~ lines guarded by ~ifndef MOD_<NAME>~, so every file parses once and ~-j~ stays safe.

A profile is ~base~ plus what it adds; that one list loads modules and orders the build:

#+begin_src makefile
BASE_MODULES := 7zip age bin env git jq lib rclone shell ssh stow vault recipes
$(foreach d,$(BASE_MODULES),$(eval include modules/$d/$d.mk))

.PHONY: base
base: sys-pkgs $(BASE_MODULES)
#+end_src

#+begin_src makefile
PHONE_MODULES := base restic            # everything else comes with base
DESKTOP_MODULES := base restic dev anki keepassxc firefox emacs xclip wireproxy
#+end_src

Make expands prerequisites lazily, so ~$(BASE_MODULES)~ at rule time is exactly what was included. Nothing listed twice.

** Package accumulation

Modules append to distro-keyed sets; the root Makefile exports them:

#+begin_src makefile
COMMON_PKGS += ripgrep tmux
DEBIAN_PKGS += emacs-gtk elpa-magit
TERMUX_PKGS += emacs
#+end_src

** The sys-pkgs barrier

Package installation is gated by one stamp per exact accumulated package set: ~.state/sys-pkgs-<cksum of all distro sets>.stamp~.

· Same package set → stamp fresh → ~install-sys-pkg~ skipped; ~make base~ re-runs in ~0.2s.
· Switching or combining goals (~make desktop lint~) → same set → still skipped. The old goal-keyed wrinkle is gone.
· Any module edit that changes a package list → new key → that set installs exactly once.
· Switching back to a previous profile → its stamp is still there → no reinstall.

Old stamps linger in ~.state/~ until ~make clean-state~; the directory is disposable at any moment.

· Module lifecycle: update and uninstall

Every module owns three make goals — ~<module>~, ~<module>-update~, ~<module>-uninstall~ — because the root Makefile strips the ~-update~/~-uninstall~ verb before the module lookup: ~make rclone-update~ loads ~modules/rclone/rclone.mk~, which defines all three. A profile (base, phone, pubnix, desktop, docker-base) forwards the verb to its members.

** make update

~make update~ refreshes every module's applied footprint in one run; each module self-skips wherever it was never applied, so on any node this composes into "update everything this node actually uses":

| Footprint                       | What update does                                                            |
|---------------------------------+-----------------------------------------------------------------------------|
| dotfile modules (env, ssh, ...) | ~dot apply~ — links point into the repo, so a pull IS the content update;    |
|                                 | restowing just picks up newly added files (and the final ~dot prune~ drops  |
|                                 | removed ones)                                                               |
| fetched tools (~/.local/bin)    | version-key check against upstream; refetch only when newer — never         |
|                                 | redownloads an unchanged latest                                             |
| the vault                      | ~vault sync~ (pull, rebase, push — the daily-operation step)                 |
| pkit and its data repos         | ~git pull --rebase~ + their own install/setup                                |
| system packages (apt/pkg)      | never touched; the host package manager owns them (loud skip per module)     |

Update never installs anything new and never talks to a package manager. There is deliberately no global ~make uninstall~: removing everything is a per-profile decision (~make phone-uninstall~), not a keystroke.

** State: the filesystem, plus a disposable version cache

"Is this module applied?" is derived, not recorded: ~dot applied~ answers it for stowed modules (any managed file linked back into the repo), and ~command -v~ plus a ~~/.local/bin~ prefix answers it for tools. No manifest to drift out of sync; deleting any state can never make the system lie.

The one thing that IS cached is the version key of each fetched tool — ~${XDG_STATE_HOME:-~/.local/state}/system/tools/<name>~ — written by ~fetch-bin~ at install time and compared by ~install-tool -u~ (for chdman, apt's candidate version; for anki, the release URL). The cache is disposable like ~.state/~: losing it costs one redundant fetch, never correctness. It lives under ~$HOME~ (not the repo) so it survives a re-clone.

** uninstall semantics

~<module>-uninstall~ removes only what this system placed: stow links, fetched binaries, cloned repos, the managed crontab (only while it still matches the module's file). System packages are never removed — that is the host's decision — and each such module says so instead of pretending. Profiles uninstall their members in reverse install order through one serial recursive make (~-j1~), with two orderings enforced: ~vault-uninstall~ runs before ~bin-uninstall~ (it needs the CLIs), and ~stow-uninstall~ runs dead last (every ~dot remove~ needs the stow binary until the final module is unstowed).

** Shared recipe macro

Stowing a module is one line in every module makefile:

#+begin_src makefile
stow-module = MODULES_DIR="$(MODULES_DIR)/$@" dot apply dotfiles
#+end_src

· Package delivery — one privilege model, one tool gate

** The privilege model (stated once)

~install-sys-pkg~ is the only thing that talks to a system package manager, and it decides privilege by itself:

| Situation                                     | Behaviour                                                       |
|-----------------------------------------------+-----------------------------------------------------------------|
| root, or Termux                               | install directly                                                |
| ~sudo -n -v~ succeeds                         | prefix the command with ~sudo~                                   |
| anything else                                 | loud skip, exit 0 — fetch fallbacks take over                    |

Provable means exactly one thing: ~sudo -n -v~ — non-interactive validation — succeeds. That covers passwordless sudo (containers, the docker-base image) and a live credential cache (a terminal that already authenticated). The probe never prompts: it fails instead of asking, so an unattended run cannot hang on a password.

Nothing short of that counts, on purpose:

- A ~sudo~ binary on PATH proves nothing — pubnix admins install sudo for themselves; every shared host has the binary.
- A seat in ~sudo~ or ~wheel~ proves nothing. ~/etc/sudoers~ is mode 0440 and unreadable, and on shared hosts those groups are exactly what an account can hold with no usable grant — absent, narrowed to specific commands, or moot under the locked password of an SSH-key-only account. Group shape cannot be probed honestly; sudo's own non-interactive answer can. It was not always so: membership in the admin groups was once accepted as proof, and commissioning on a real pubnix prompted for a password that could never authenticate — while CI, whose test user sat in no admin group, stayed green. The group branch is gone, and the CI user now sits in ~wheel~ so the decoy can never regress unnoticed.
- A password prompt is not a probe. Sprung on an unattended run it hangs; sprung on a pubnix it asks for a password that cannot authenticate. Either way it is a broken commissioning, so no code path may reach for one.

Two consequences, both accepted:

1. On your own password-sudo PC, authenticate first — ~sudo -v~ in the terminal you will run ~make~ from — and the live cache carries the install. One command, nothing to configure.
2. An account with command-specific grants (hand-written ~sudoers.d~ entries) is skipped loudly too; install those by hand — typing ~sudo apt-get install …~ still works.

There is no ~SUDO~ variable, nothing to export, nothing to remember. ~bootstrap~ does not second-guess this: it hands package work to ~install-sys-pkg~ and only dies clearly when the host cannot provide GNU make.

** install-sys-pkg (dual-mode installer)

· Batch (from Make): no arguments. Unions ~COMMON_PKGS~ with the current distro's set, deduplicates, installs.
· Standalone: ~install-sys-pkg ripgrep tmux fzf~ installs ad hoc.
· Rootless: prints a loud skip naming the packages the host must provide.

** install-tool (the apt-or-.local gate)

Every module tool goes through one gate — ~install-tool [-u] <name> <source> [asset-pattern] [archive-binary]~ — whose PATH check is the single source of truth for "is it installed":

1. Already on PATH → skip (it came from apt, pkg, or a previous fetch — all the same).
2. Otherwise fetch the static binary into =~/.local/bin= via ~fetch-bin~.

With ~-u~ the same gate updates: absent tools skip ("not installed"), host-provided tools skip ("owned by the host"), and fetched tools compare the recorded version key against what upstream currently serves — downloading only on a real change. Its mirror ~uninstall-tool <name>~ removes the fetched copy and nothing else.

So the same one-line rule covers every node type: Debian installs ~jq~ through apt and skips the fetch; Termux installs it through ~pkg~ and skips; a pubnix fetches it. Patterns may use placeholders substituted from the OS engine — ~{OS}~, ~{ARCH}~ (Go-style ~amd64~), ~{XARCH}~ (vendor-style ~x64~, as 7zip names it). On Termux ~{OS}~ substitutes ~linux~, because upstream archives never publish "android" assets — their static linux builds are what run there:

#+begin_src makefile
.PHONY: jq
jq: sys-pkgs
        @install-tool jq gh:jqlang/jq 'jq-{OS}-{ARCH}$$'
#+end_src

Tools that need more than a fetch keep a real ~install~ script (~anki~, ~chdman~, ~stow~ — source build on rootless hosts).

** Library contract

One library, ~lib/sh/lib.sh~ (OS engine + fetch engine), resolved through exactly two locations: ~$LIB_DIR~ (exported by Make and by ~bootstrap~, pointing at the repo) or =~/.local/lib= (installed, standalone use):

#+begin_src sh
LIB="${LIB_DIR:-$HOME/.local/lib}/sh/lib.sh"
[ -f "$LIB" ] || { echo "<script>: lib.sh not found at $LIB (run 'make base' first)" >&2; exit 1; }
# shellcheck source=/dev/null
. "$LIB"
#+end_src

~bootstrap~ is no longer a special case: it sets the same ~PATH~/~LIB_DIR~ the Makefile uses, then delegates everything else.

** fetch-bin (binary fallback engine)

Installs prebuilt binaries to =~/.local/bin= from direct URLs or GitHub releases (~gh:owner/repo~ plus asset regex), extracting common archive formats. Archive type is taken from the URL actually served: a generic basename like ~dl.filippo.io/age/latest~ is resolved by a single HEAD probe, because the redirect names the real asset (~age-v1.3.2-linux-amd64.tar.gz~). Candidate selection when no binary name given:

1. A file exactly matching the expected name.
2. Otherwise, the archive's single executable file.
3. Otherwise, the archive's single regular file.
4. Anything ambiguous fails loudly, listing every candidate.

Accepted trade: no checksum or signature verification. fetch-bin trusts HTTPS and the source. Reasonable for a personal system; do not copy into anything multi-user.

Every successful fetch records its version key (resolved release URL) under ~${XDG_STATE_HOME:-~/.local/state}/system/tools/~ — the disposable cache ~install-tool -u~ compares against.

· Dotfile management (~dot~)

~dot~ wraps GNU Stow with conflict-safe preparation and a lock for parallel make.

· ~--no-folding~, always. Directories in ~$HOME~ stay real; only leaf files are symlinked.
· Unmanaged host files blocking a link are kept beside themselves as ~.a.bak~ (latest wins) before Stow runs — never overwritten, never destroyed.
· Stale or overridden symlinks removed so Stow relinks cleanly.
· Shared directories (=~/.config/autostart/=) accept files from multiple modules without collision.
· Concurrency: ~flock~ on =~/.local/state/dot.lock= serializes ~dot~ under ~make -j~.
· Standalone: an installed ~dot~ is a symlink back into the repo, so ~dot ls~ / ~dot prune~ infer the module tree from their own referent and work from any directory.

Hygiene: when a file is removed from a module, its link goes stale. ~dot prune~ removes broken links whose target resolves under ~MODULES_DIR~; foreign broken links are never touched. Run after pulls that delete files. Known limit: if an entire module directory is deleted from the repo, prune can no longer attribute its links — remove such modules properly first (~dot remove <module>~).

#+begin_src sh
dot apply <module...>          # MODULES_DIR=<module-dir> dot apply dotfiles
dot remove <module...>
dot prune
dot applied <module...>        # exit 0 iff linked back into the module
dot ls
#+end_src

· Sovereign vault

Private configuration, SSH keys, credentials, and machine-specific secrets live in an unencrypted Git repository at =~/.vault/=, mirroring the module layout of the system repo (~ssh/~, ~git/~, ~rclone/~, ~base/~, …). At rest protected by filesystem permissions (0700 dirs, 0600/0700 files, clamped on every apply/sync) and the disk/host itself; in transit by age encryption (the seed) or SSH (git push/pull).

~make vault~ applies ~VAULT_MODULES~ — declared once in ~modules/vault/vault.mk~ because every profile wants the same set, overridable per invocation (~make vault VAULT_MODULES="ssh git"~). Applying an unknown vault module fails loudly. On a node with no vault yet, the profile prints a loud skip and continues — commissioning is not blocked by secrets that have not arrived yet. On an established node, treat that skip as a fault.

** vault sync semantics

~sync~ commits local changes, rebases on upstream, and pushes:

· Pull happens only once an upstream exists — the first sync after ~vault init <url>~ just pushes.
· Push failures are not masked: network or auth failure exits nonzero with git's own error visible; ~vault: synced~ prints only after a real push.
· With no remote configured, sync says so explicitly and keeps the commit local.

** Usage

#+begin_src sh
vault init [remote-git-url]   # clone, adopt a restored seed, or init empty
vault sync
vault apply <module...>
vault remove <module...>
vault chmod
vault ls
vault git <command...>        # pass-through
#+end_src

· Layering: tools first, secrets later

The system is commissioned in honest layers, so "just the tools" is always a valid stopping point:

#+begin_example
host baseline      git, make (gmake), curl, perl, bash, archive tools
      │            (the admin's job on a rootless host)
      ▼
bootstrap <profile>          TOOLS — no secrets needed or touched
      │                      base: dot/vault CLIs, stow, fetches
      ▼
vault arrives     one of: cold seed · agent forwarding · fresh identity
      │
      ▼
make vault                   SECRETS — links ssh/git/rclone/... from ~/.vault
      │
      ▼
secret-dependent modules     pkit-meta, pkit-archive (clone private repos
      │                      over SSH using the vault's keys)
      ▼
daily operation    make <profile> · dot prune · vault sync
#+end_example

This is why ~docker-base~ (and any profile) is secret-optional: in a disposable container you often want exactly the tools and nothing else. Modules that require secrets (~pkit-meta~, ~pkit-archive~) declare ~vault~ as a make prerequisite, so the ordering is enforced by the DAG: on a node without a vault their ~git clone~ fails loudly — the honest signal that the secrets layer is missing, not a bug.

· Commissioning a node

** The trust problem (read this first)

The system repo is clonable over HTTPS from anywhere. The vault is private: cloning it needs an SSH key that, on a fresh node, does not exist yet — and the keys themselves live inside the vault. Three ways to break the circle, in order of preference:

1. Cold seed — carry one age-encrypted file from a trusted node. Works everywhere, including phones and hosts you only half-trust.
2. SSH agent forwarding — borrow a trusted machine's agent for the first clone only. Fastest on a pubnix you administer interactively.
3. Fresh identity — generate a new key on the node and register it with the git host. Most revocable, most manual.

Whichever method: the first ~./bootstrap <profile>~ run completes with a loud =vault: ~/.vault missing -- skipping vault apply= notice. That is expected — the tools layer is done. Bring the vault over, then run ~make vault~ (the secrets layer).

** Method 1 — cold seed

On a trusted node (your PC), create the seed. The archive contains the whole vault, including ~.git~ history and the origin remote:

#+begin_src sh
backup create ~/.vault ~/vault-seed.tar.gz.age
#+end_src

This encrypts to the first recipient in =~/.config/age/recipients.txt=. The matching identity (=~/.config/age/keys.txt=) is itself inside the vault, so a fresh node cannot decrypt this seed until the identity is placed first. Two honest ways to handle that:

· Pass the identity file ahead of the seed (the "set a file and pass it" path):
  #+begin_src sh
  ssh user@newnode 'mkdir -p ~/.config/age'
  scp ~/.config/age/keys.txt user@newnode:~/.config/age/keys.txt
  scp ~/vault-seed.tar.gz.age user@newnode:~/
  #+end_src
  Then on the new node: ~backup restore ~/vault-seed.tar.gz.age ~/.vault~.
· Or make a passphrase-encrypted seed instead, so nothing but a passphrase travels:
  #+begin_src sh
  tar -C "$HOME" -czf - .vault | age -p -o ~/vault-seed.tar.gz.age
  #+end_src
  Restore on the new node (no identity file needed):
  #+begin_src sh
  mkdir -p ~/.vault
  age -d ~/vault-seed.tar.gz.age | tar -C ~/.vault --strip-components=1 -xzf -
  #+end_src

Transport by scp, USB, or Syncthing — never plaintext, never a public paste. ~vault-seed~ and ~.age~ are git- and docker-ignored, so a seed cannot leak into a commit or an image by accident. Delete the seed from both ends once the node is commissioned.

After restore, adopt in place and apply:

#+begin_src sh
vault init          # sees .git from the seed; clamps permissions
make vault          # applies VAULT_MODULES (ssh base git rclone)
#+end_src

** Method 2 — SSH agent forwarding (pubnix first login)

On the trusted machine, confirm the agent holds a key the git host accepts, then forward it for this one session:

#+begin_src sh
ssh-add -l                      # must list your vault key
ssh -A user@pubnix.example      # or: ForwardAgent yes per-host in ssh config
#+end_src

On the pubnix, commission normally, then clone the vault through the forwarded agent:

#+begin_src sh
git clone https://github.com/esperoj/system.git ~/projects/system
cd ~/projects/system
./bootstrap pubnix              # completes; vault step skips loudly
vault init git@codefloe.com:esperoj/vault.git
make vault                      # stows the vault's SSH keys onto this host
#+end_src

From that point the node holds its own copy of the keys; ~vault sync~ and git need no forwarding anymore. Log out of the forwarded session.

Security note: while forwarded, anyone who can reach the agent socket on that host (notably its admins) can use your key. Forward only to hosts you trust at least as much as the key; prefer the cold seed otherwise, or use ~ssh-add -c~ so each use asks for confirmation locally.

** Method 3 — fresh identity

#+begin_src sh
ssh-keygen -t ed25519 -C "esperoj@<node>"
cat ~/.ssh/id_ed25519.pub       # register this on the git host
vault init git@codefloe.com:esperoj/vault.git
make vault
#+end_src

~make vault~ then links the vault's own keys into ~$HOME~; ~dot~ keeps the fresh key beside itself as ~.id_ed25519.bak~ first. Revoke the fresh key on the git host once the vault keys are in place, if unwanted.

** PC (Debian 13+)

#+begin_src sh
git clone https://github.com/esperoj/system.git ~/projects/system
cd ~/projects/system
./bootstrap desktop             # installs make if missing, then the profile

bring the vault over (Method 1/2/3), then:

make vault
make setup-remotes              # ssh remotes, dual push github + codefloe
exec bash -l
#+end_src

** Phone (Android / Termux)

Fresh Termux has no git. Install it, grant storage, then commission:

#+begin_src sh
pkg update && pkg install -y git
termux-setup-storage            # needed for /sdcard backups and workspace
git clone https://github.com/esperoj/system.git ~/projects/system
cd ~/projects/system
./bootstrap phone

bring the vault over — cold seed is the natural path on a phone:

scp vault-seed.tar.gz.age phone:~/   (or USB / Syncthing)

backup restore ~/vault-seed.tar.gz.age ~/.vault   # identity placed first
vault init && make vault
exec bash -l
#+end_src

Nothing else is needed beforehand: the Termux app starts every session through ~login~, which preloads ~termux-exec~ (its ~execve()~ hook rewrites ~#!/bin/sh~ shebangs to the Termux prefix) before starting the shell, and ~bootstrap~ installs ~make~ itself through ~install-sys-pkg~ the first time it is missing. CI reproduces the phone inside ~termux/termux-docker~ the same way: the whole commissioning script runs through ~login -c~, the exact entry point a device uses. (The image starts ~bash~ without the preload, and exporting ~LD_PRELOAD~ mid-script comes too late — the hook must live in the process that calls ~execve~, so it has to be set before the shell starts.)

** Pubnix (shared rootless UNIX)

Expectations, honestly: you have no root, and nothing to configure — privilege is auto-detected, and neither the ~sudo~ binary the admins left on PATH nor any admin-shaped group your account sits in (~wheel~, ~sudo~) is read as yours; on a shared host both can exist with no grant behind them. The host must already provide ~git~, ~make~ (~gmake~ on FreeBSD), ~curl~, ~perl~, ~bash~, and the archive tools the fetches need (~unzip~, ~xz~, ~bzip2~). Without usable sudo, ~install-sys-pkg~ skips loudly; ~stow~ falls back to a source build into =~/.local=; ~install-tool~ fetches the rest into =~/.local/bin=. Anything neither present nor fetchable needs the host admin.

#+begin_src sh
ssh -A user@pubnix.example      # Method 2; or carry a seed (Method 1)
git clone https://github.com/esperoj/system.git ~/projects/system
cd ~/projects/system
./bootstrap pubnix              # no SUDO=echo, no exports, nothing
vault init git@codefloe.com:esperoj/vault.git   # via the forwarded agent
make vault
exec bash -l
#+end_src

=~/.profile= handles pubnix quirks (per-host ~TMPDIR~, python paths). crontab availability depends on the host's policy.

** Container (docker-base)

#+begin_src sh
docker build -t system:base .
docker run -it --rm system:base
#+end_src

The image runs ~./bootstrap docker-base~ at build time as non-root user ~esperoj~, who holds passwordless sudo for ad-hoc installs — a container-only convenience for disposable environments. NOPASSWD has no place on a persistent host. No secrets are baked in: ~.vault~, ~.age~, and ~vault-seed~ are docker-ignored; the vault step skips loudly in the build log by design. Want only the tools in a container? That is exactly what this profile is — commission the vault inside a running container with Method 1 or 2 if needed.

** Verification checklist (every node)

· Daily operation

#+begin_src sh
cd ~/projects/system
git pull --rebase
make desktop                    # or phone / pubnix / docker-base
make update                    # tools, links, vault, repos — skips what is latest
dot prune                       # after pulls that removed files (make update does this too)
vault sync                     # honest exit codes
#+end_src

Isolated modules: ~make emacs~, ~make git~, ~make dev~. Lifecycle verbs: ~make rclone-update~, ~make rclone-uninstall~, ~make phone-update~, ~make phone-uninstall~. Ad-hoc packages: ~install-sys-pkg ripgrep~. Ad-hoc tools: ~install-tool fzf gh:junegunn/fzf 'fzf-{OS}-{ARCH}$$'~. Force full package re-evaluation: ~make clean-state && make <profile>~ (switching profiles does not need clean-state). Inspect before running: ~make -n <goal>~.

Shell completion: ~make <TAB>~ completes every profile, module and verb on PC, phone and pubnix — the shell module stows a user-local bash completion that sees the goal-driven targets the stock one cannot (works with or without the bash-completion package).

· Continuous integration

GitHub Actions (~.github/workflows/ci.yml~) exercises the system on every push and pull request:

| Job             | What it proves                                                      |
|-----------------+---------------------------------------------------------------------|
| ~lint~          | shellcheck + shfmt pass on every script                             |
| ~debian-image~  | ~docker build~ of the Dockerfile; CLIs and ~dot ls~ inside the image |
| ~debian-rootless~ | a pubnix simulation: unprivileged user in the ~wheel~ decoy group, ~sudo~ on PATH (behind a logging shim) but no rights to it — commissioning + ~make update~ + ~make jq-uninstall~ complete with sudo probed (~-n -v~) but never used, loud skip asserted, user-local fetch fallbacks |
| ~termux~        | the full phone profile commissioned inside ~termux/termux-docker~ (with ~termux-exec~ preloaded, as on a device), then a no-op re-run and ~make update~ (host-owned skips) |

Image publishing to the codefloe registry stays in ~.crow/publish.yaml~ (cron/manual).

· Code quality contract

~make lint~ runs shellcheck at default severity plus ~shfmt -d~. No blanket suppressions. Exactly two classes of finding are disabled, each inline at its use site with its reason:

1. Dynamic library sources (~# shellcheck source=/dev/null~): ~lib.sh~ resolves through ~$LIB_DIR~ or =~/.local/lib= at runtime.
2. Deliberate word-splitting in ~install-sys-pkg~: ~$PKGS~ splits line-per-package to deduplicate, and ~$SUDO~ is empty or exactly ~sudo~.

A new warning is fixed, or it joins this list with a justification. Silence is never the default. ~make fmt~ formats in place. ~make review~ sends the latest commit to an AI reviewer with this file (~README.org~) as context; needs network access and is a convenience, not part of the build.
